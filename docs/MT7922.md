# MediaTek MT7922 / MT7921 (`mtkradio`) Bring-Up & Findings

This note summarizes the verified hardware bring-up, protocol findings, and Windows 11 / Linux throughput benchmarks for MediaTek Connac2 Wi-Fi 6/6E cards driven by `mtkradio` (also published standalone at [YiHoooong/mtkradio](https://github.com/YiHoooong/mtkradio)).

## Supported PCI IDs & Firmware

| Chip | PCI Vendor:Device | Firmware (`radio\firmware\`) |
|---|---|---|
| MediaTek MT7922 / AMD RZ616 | `14C3:0616`, `14C3:7922` | `WIFI_MT7922_patch_mcu_1_1_hdr.bin`, `WIFI_RAM_CODE_MT7922_1.bin` |
| MediaTek MT7921 / AMD RZ608 | `14C3:7961`, `14C3:0608` | `WIFI_MT7961_patch_mcu_1_2_hdr.bin`, `WIFI_RAM_CODE_MT7961_1.bin` |

- Driven via the same on-PC self-signed UMDF register proxy (`winawdl_regproxy`, `WUDFRd`) as Intel cards — no `TESTSIGNING` or EV/WHQL certificate required.
- Requires `SeLockMemoryPrivilege` for 32-bit DMA pages (`AllocateUserPhysicalPages`), satisfied automatically when launched by `NekoDropService` (`LocalSystem`).
- Boots MT7922 ROM patch + RAM firmware in **~280 ms**, supports `OnDemand` mode (returns the card cleanly to MediaTek's `mtkwlex` driver when idle), and includes **experimental Concurrent mode (5 GHz Wi-Fi beside AirDrop, untested on hardware)**.

## Verified Hardware & Protocol Findings (Windows 11 + MT7922)

Live tests on Windows 11 26H2 (`PCI\VEN_14C3&DEV_0616`, AMD RZ616) with iPhone AirDrop uncovered five key bottlenecks and protocol constraints:

1. **`awdld` (OWL) vs. `owly` ADDBA / A-MSDU behavior**:
   - `awdld` (OWL) does not reply to incoming 802.11 `ADDBA Request` frames and cannot parse 802.11 A-MSDU frames (`unhandled frame (-1)`).
   - `mtkradio` therefore auto-answers `ADDBA Request` with **`amsdu = 0`** (matching `iwxradio/src/awdl_policy.h`) when serving `awdld`, activating MT7922 hardware RX BlockAck (`STA_REC_BA`, 64-frame A-MPDU window) without triggering A-MSDU drops.
   - When driven by an AWDL stack that manages its own ADDBA and slot schedule (such as `owly` via `--no-block-ack`, branch `YiHoooong/owly@feat/windows-mtkradio`), `mtkradio` bypasses `unicast_q` / `awdl_sched` completely for 100% raw passthrough.

2. **Windows 15.6 ms default timer tick**:
   - Without `timeBeginPeriod(1)`, Windows AWDL timers suffer ~8.3 ms average / 17 ms max jitter.
   - Enabling `timeBeginPeriod(1)` cuts timer jitter ~7x to **1.2 ms avg / 2.8 ms max**.

3. **Windows 64 KiB Wintun TCP buffer cap (biggest RX lever)**:
   - Windows defaults TCP `SO_RCVBUF` / `SO_SNDBUF` on Wintun (`awdl0`) to ~64 KiB, capping throughput across AWDL's 20–100 ms slot-hop RTTs to **~0.55 MB/s**.
   - Raising `SO_RCVBUF` / `SO_SNDBUF` to **2 MiB** + `TCP_NODELAY` (tracked separately so Intel's engine path stays untouched in this PR), combined with 512 KiB batched Named Pipe I/O, 5 ms active spin before `Sleep(1)`, and batched WFDMA `CIDX` doorbells, jumped MT7922 Windows 11 RX **7.5x**:
     - **4.3 MB photo**: `< 6 s` (~0.8 MB/s, 0 drops)
     - **394 MB APK (`com.primatelabs.geekbench6.apk`)**: **4.5 MB/s peak** (16,626 RX frames / 10 s), **1.14 MB/s sustained average**, 146,401 frames received with **0 queue drops**.

4. **iOS 15-second 4/16 AWDL duty-cycle cliff**:
   - During the 394 MB transfer, iOS granted AWDL ~16/16 slots (**4.5 MB/s**) for the first ~15 s, then dropped to its shared Wi-Fi coexistence schedule of **4/16 slots = 25%** (`4,000 / 16,626 = 24.1%`, **~1.1 MB/s**) to hop off-channel to its associated AP.
   - Allowing 802.11 hardware short retries (`no_ack = false`) on unicast TCP ACKs avoids losing an entire 256 ms superframe on a single collision.

5. **Hardware TX BlockAck (`MT_BA_TYPE_ORIGINATOR`) + VHT 80 MHz 2SS + EDCA TXOP (biggest TX lever)**:
   - Without TX A-MPDU, non-aggregated PC → iPhone sending caps at **~280 KB/s** (~3 frames per 16 ms slot).
   - Adding Radiotap VHT (bit 21) decoding (`MT_PHY_TYPE_VHT`, 80 MHz 2SS, SGI, LDPC), Connac2 `STA_REC_BA` / `WTBL_BA` originator (`MT_BA_TYPE_ORIGINATOR = 1`, clearing `MT_TXD3_BA_DISABLE` on peer `wcid`), and EDCA `txop = 94` (~3 ms) activated both `HW TX BA` and `HW RX BA` live on MT7922:
     - **10.7 MB photo (PC → iPhone)**: delivered 100% cleanly (`0 drops`), bursting **6.78 MB in ~4 s (~1.7 MB/s, 6x faster than non-aggregated TX)**.
     - Remaining work for sustained 5–15+ MB/s TX: A/B tune `OWLY_VHT_MCS` / `OWLY_NO_AMSDU` to eliminate the mid-transfer TCP CWND backoff.

## Concurrent Wi-Fi + AirDrop (Experimental, Untested on Hardware)

Concurrent mode for MT7922 / MT7921 follows the same host-side design proved on MT7902 (`mtradio/`, PR #47), reusing shared code rather than forking it:

- **Shared station & crypto**: `mtkradio/src/mtk_station.*` implements `StaDevice` (`iwxradio/src/sta_device.h`) to drive `iwxradio/src/wifi_sta.*` (join, WPA2/WPA3, TAP bridge) with `mtradio/src/ccmp.*` (CNG host-side CCMP, verified by `ccmp_test` in `scripts/build-radio-mtk.ps1`).
- **Second own address & AP STA record**: `MtkDevice` adds own MAC 1 / BSS 1 (`MCU_UNI_CMD_DEV_INFO_UPDATE` + `MCU_UNI_CMD_BSS_INFO_UPDATE`, `CONNECTION_INFRA_AP`) so the MAC ACKs the AP's frames to the TAP address, and registers the AP on reserved WTBL slot 18 (`kApWcid = 18`; AWDL peers stay in slots `1..17`) from the beacon's HT/VHT capabilities (`STA_REC_BASIC`, `STA_REC_HT`, `STA_REC_VHT`, `STA_REC_PHY`, `STA_REC_RA`, `STA_REC_STATE`, `STA_REC_WTBL`). Unicast data to the AP goes out as QoS data at the firmware's rate; the AP's receive Block Ack sessions are accepted with a per-TID host reorder buffer (20 ms on-channel gap timeout, BAR handling, AP frames to other clients dropped), while TX BA towards the AP is intentionally disabled.
- **Single-channel time-sharing & scans**: `mtkradio/src/mtk_main.cpp` accepts `--sta-config <file>` and `--country <CC>`, listens on `stdin` for `scan [SSID hex]` and `rejoin`, and emits `event: wifi ...` / `event: bss ...` / `event: scan-done ...` for `NekoDropService`. When the AP is on the same 5 GHz channel as AWDL, both share it with zero hops; on another 5 GHz channel, the scheduler clocks from `awdld`'s sync TLV (4) channel sequence, rewrites our outgoing AWDL channel sequence (`coex_plan.h`), gives Wi-Fi 12/16 entries when AirDrop is idle (or Apple's coexistence table while AirDrop moves data), sends power-save null frames around RF-only `MCU_EXT_CMD_CHANNEL_SWITCH` moves, and holds station/AWDL frames while off channel.

### Gated / Unverified Without Hardware

The following pieces compile and match the Connac2 / `mt7921` protocol, but have **not yet been verified on real MT7922 or MT7921 hardware**:

1. **5 GHz-only gate (`StationOn24GHz: false`)**: Like MT7902 (where 2.4 GHz ACKed TX never completed), `MtkRadioCaps` restricts Concurrent mode to 5 GHz (`mtk_main.cpp` also refuses 2.4 GHz `--sta-config` with `event: wifi failed`) because 2.4 GHz ACKed frame completion has not been tested on MT7922/MT7921.
2. **TX-free completion reports (`PKT_TYPE_TXRX_NOTIFY`)**: `MtkDevice::handle_tx_free()` follows Linux `mt7921_mac_tx_free` and is wired across `_rx_mcu`, `_rx_mcu_wa`, `_rx_data`, and `mcu_wait_response()`. Hardware verification is needed to confirm which RX ring delivers `PKT_TYPE_TXRX_NOTIFY` on MT7922/MT7921 firmware and that PS-null ACKs and rate-ladder fallback receive completions reliably.
3. **RF-only channel-switch latency & BAR delivery**: `move_timeout_ms` is set to 60 ms (with one retry on failure) and `RFCR` keeps control BAR frames addressed to own MAC 1; actual channel-switch latency, coexistence throughput, and firmware stability under concurrent AP RX BA + AWDL traffic need live testing.
4. **MT7921 (`14C3:7961` / `0608`)**: Neither On-Demand nor Concurrent mode has been tested on MT7921 hardware yet.
